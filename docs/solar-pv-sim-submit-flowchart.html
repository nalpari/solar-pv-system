시뮬레이션 제출 게이트

세 단계가 순서대로 있고, 순서 자체가 설계다 — 파라미터 검증이 이미지 업로드보다 먼저다. 뒤집으면 검증 실패마다 S3 에 고아 객체가 쌓인다. 어느 단계에서 막히든 도착지는 하나다.

Ordering

왜 검증이 업로드보다 먼저인가

  • 파라미터가 틀리면 S3 에 쓸 이유가 없다 — 순서를 바꾸면 검증 실패마다 고아 객체가 쌓인다
  • 현재 순서에서도 ③ 이후 사용자가 결과 페이지를 떠나면 객체는 남는다. 정리 로직이 없으므로 버킷 라이프사이클이 필요하다
  • 우편번호는 검색 결과를 재사용하지 않고 항상 최종 크롭 중심을 역지오코딩한다 — 검색 후 지도를 옮겨 다른 건물을 크롭할 수 있어서다

Retry policy

③ 만 재시도한다

  • getLayoutBlob() 이 없으면 재시도 무의미 — 즉시 null
  • 4xx(빈 파일·용량 초과)는 결정적 실패 — 즉시 중단
  • 그 외에는 최대 3회, attempt * 500ms 백오프
  • ①·②는 재시도하지 않는다

Fidelity ledger

이 그림에서 뺀 것

  • canSubmitSim 6조건 — 버튼 활성화 게이트라 제출 흐름 밖이다
  • buildSimulationInput 매핑 (ROOF_LOC_CD · SUN_TO_DEGREE) — 미매핑 값을 조용히 0 으로 떨어뜨린다
  • 팝업 차단 시 현재 탭 이동으로 폴백하는 분기
  • 바깥 try/catch 의 네트워크 예외 경로 — 도착지는 같은 중단이다
