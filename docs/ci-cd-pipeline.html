03스테이지 상세

3.1  Checkout

Jenkins 기본 체크아웃을 끄고 스테이지 안에서 GitSCM 을 직접 부른다. 잡 설정에 어떤 브랜치가 걸려 있든 실제 빌드 대상은 PROFILE 이 정한다.

def targetBranch = params.PROFILE == 'prod' ? 'main' : 'dev'
checkout([$class:'GitSCM', branches:[[name:"*/${targetBranch}"]],
          userRemoteConfigs: scm.userRemoteConfigs, extensions: scm.extensions])

3.2  Load Env Credential

Credential ID종류역할
pv-common-envSecret filedev/prod 공통 — Maps · OpenRouter · AWS S3
pv-dev-envSecret filedev 전용 — QSP/MUSBI 호스트, 문서 노출 플래그, Origin 허용목록
pv-prod-envSecret fileprod 전용 — 동일 키의 운영 값
cat "$ENV_COMMON" > .env
printf '\n' >> .env      # 공통 파일 끝에 개행이 없어도 첫 프로파일 키가 붙지 않도록
cat "$ENV_PROFILE" >> .env
chmod 600 .env

병합 순서 = 우선순위. set -a; . ./.env 로 소싱하므로 같은 키를 다시 정의하면 나중 값(프로파일)이 이긴다.

3.3  Validate Environment

.env 소싱 후 필수 키 12개를 : "${VAR:?메시지}" 로 전수 검증한다.

공통  NEXT_PUBLIC_GOOGLE_MAPS_API_KEY  OPENROUTER_API_KEY  OPENROUTER_MODEL
       AWS_REGION  AMPLIFY_BUCKET  AWS_ACCESS_KEY_ID  AWS_SECRET_ACCESS_KEY
       NEXT_PUBLIC_AWS_S3_BASE_URL
프로파일  QSP_API_HOST  MUSBI_API_HOST  ENABLE_API_DOCS  ALLOWED_ORIGIN
미검증(선택값)  REPLICATE_API_TOKEN  MUSBI_CHECK_PATH  MUSBI_RESULT_PATH  MUSBI_RESULT_HOST
미검증(잔존)    GEMINI_API_KEY  GEMINI_MODEL   ← 미사용. 롤백 대비로 남겨둔 여분 키
놓치면 아픈 곳

새 환경변수를 추가하면 이 스테이지에 검증 라인을 반드시 같이 추가한다. 빠뜨리면 값이 비어 있어도 배포가 “성공”하고, 런타임에 500(추론/S3) 또는 403(ALLOWED_ORIGIN 미설정 시 모든 POST)으로 나타난다.

2026-07-30 OpenRouter 전환으로 GEMINI_API_KEY · GEMINI_MODEL 검증 2줄이 OPENROUTER_* 로 교체됐다. 검증하지 않는 여분 키는 파이프라인을 실패시키지 않으므로 잔존 GEMINI_* 는 무해하다.

3.4  Verify — 두 검사의 실패 정책이 다르다

① OKF 번들 신선도 — 비차단. 문서 문제로 배포를 막지 않는다는 게 명시된 정책이다.

bash docs/okf/check.sh || echo '[okf] 경고가 있습니다 — 배포는 계속합니다.'
  • pnpm okf:check 가 아니라 bash 로 직접 부른다 — Jenkins 에이전트에 Node 가 없고, check.sh 는 bash + git 만 쓴다.
  • bash 자체가 없으면 조용히 건너뛴다.
  • 긴 docker build 로그에 묻히지 않도록 빌드보다 먼저 실행한다.

② 빌드 검증 — 차단.

docker build --target builder \
  --build-arg NEXT_PUBLIC_GOOGLE_MAPS_API_KEY="$NEXT_PUBLIC_GOOGLE_MAPS_API_KEY" \
  --build-arg NEXT_PUBLIC_AWS_S3_BASE_URL="$NEXT_PUBLIC_AWS_S3_BASE_URL" \
  -t "solar-pv-system:verify-${BUILD_NUMBER}" .
docker rmi "solar-pv-system:verify-${BUILD_NUMBER}" || true

builder 스테이지 안에 pnpm lint → pnpm exec tsc --noEmit → pnpm build 가 들어 있어 린트·타입 실패가 곧 이미지 빌드 실패다. 검증용 태그는 바로 지우지만 레이어 캐시는 남아 Deploy 의 compose build 가 그대로 재사용하므로 이 중복 빌드는 거의 공짜다.

3.5  Deploy

단계devprod
빌드compose --profile dev build app-devcompose --profile prod build app-prod-4000
태깅:dev-{N} → :dev-latest:prod-{N} → :prod-latest
기동up -d --wait app-devup -d --wait app-prod-4000 app-prod-4001
정리숫자 태그 최근 2개만 보존 (KEEP_VERSIONS=2)

--wait 가 배포 게이트다. 컨테이너 healthcheck 가 healthy 가 될 때까지 블로킹하고, unhealthy 로 끝나면 비0 종료해 스테이지를 실패시킨다.

prod 의 4001 은 4000 의 이미지를 재사용한다. app-prod-4001 에는 build: 섹션이 없고 image: 만 있으므로 4000 을 먼저 빌드해 태그를 만들어야 뜬다 — depends_on 도 그래서 걸려 있다.

# 이미지 정리 — {profile}-{숫자} 형태만 골라 역순 정렬 후 3번째부터 삭제
docker images --format '{{.Repository}}:{{.Tag}}' \
  | grep -E "^solar-pv-system:${profile}-[0-9]+$" \
  | sed "s/^solar-pv-system:${profile}-//" | sort -n -r \
  | tail -n "+3" | sed "s/^/solar-pv-system:${profile}-/" | xargs -r docker rmi || true

정규식이 숫자 태그만 잡으므로 -latest 와 다른 프로파일 이미지는 삭제되지 않는다.

3.6  post { always }

.env 를 지워도 컨테이너는 멀쩡한 이유

env_file 은 컨테이너 생성 시점에 읽혀 환경변수로 굳는다. 다만 워크스페이스에 .env 가 남지 않으므로, 이후 수동으로 docker compose 를 다시 부르려면 .env 를 직접 만들어야 한다.

04이미지 — Dockerfile 4스테이지

base     node:20-alpine + corepack pnpm@10
 ├─ deps     package.json + pnpm-lock.yaml → pnpm install --frozen-lockfile
 └─ builder  deps 의 node_modules + 소스 전체
              ARG/ENV NEXT_PUBLIC_GOOGLE_MAPS_API_KEY, NEXT_PUBLIC_AWS_S3_BASE_URL
              RUN pnpm lint
              RUN pnpm exec tsc --noEmit
              RUN pnpm build            → .next/standalone
runner   node:20-alpine (builder 와 별개 베이스)
          NODE_ENV=production · 비루트 nextjs(uid 1001)/nodejs(gid 1001)
          COPY public, .next/standalone, .next/static
          EXPOSE 3000 · PORT=3000 · HOSTNAME=0.0.0.0 · CMD ["node","server.js"]
#포인트
1의존성 레이어 분리 — deps 가 락파일만 복사하므로 소스만 바뀐 빌드는 pnpm install 을 건너뛴다.
2검증이 빌드 안에 있다 — CI 스크립트가 아니라 Dockerfile 이 lint/tsc 를 수행한다. 로컬 docker build 도 같은 게이트를 통과한다.
3NEXT_PUBLIC_* 는 빌드타임 — 클라이언트 번들에 문자열로 인라인된다. 값을 바꾸려면 재시작이 아니라 재빌드가 필요하다.
4runner 는 pnpm 없이 뜬다 — output: "standalone" 산출물만 복사해 이미지가 작고 node_modules 가 없다.
.dockerignore

node_modules · .next · .git · *.md · .env · .env.local · .env*.local 제외 — 빌드 컨텍스트에 .env 가 절대 들어가지 않는다. 시크릿은 오직 --build-arg(빌드타임 2개)와 env_file(런타임)로만 들어온다.

05런타임 — docker-compose.yml

서비스profiles:이미지포트빌드
app-devdev:dev-${IMAGE_TAG:-latest}4010:3000O
app-prod-4000prod:prod-${IMAGE_TAG:-latest}4000:3000O
app-prod-4001없음:prod-${IMAGE_TAG:-latest}4001:3000X (4000 이미지 재사용)

공통: env_file: .env · NODE_ENV=production · restart: unless-stopped · 공유 healthcheck 앵커.

x-app-healthcheck: &app-healthcheck
  test: ["CMD", "wget", "-q", "--spider", "http://127.0.0.1:3000/"]
  interval: 5s      # 최대 대기 ≈ start_period 10s + 12회 × 5s
  timeout: 3s
  retries: 12
  start_period: 10s
헬스체크를 외부 curl 로 바꾸지 말 것

Jenkins 에이전트가 DooD(Docker-outside-of-Docker) 컨테이너라 호스트 publish 포트(4000/4010)에 닿지 못한다. 그래서 컨테이너 안의 busybox wget 으로 127.0.0.1:3000 을 찌른다. curl localhost:4000 방식으로 바꾸면 Jenkins 에서 반드시 실패한다.

app-prod-4001 에 profiles: 키가 없다

compose 에서 프로파일이 없는 서비스는 항상 대상에 포함되므로 --profile dev 로 올릴 때도 딸려올 수 있다. Jenkinsfile 이 서비스명을 명시(up -d --wait app-dev)해서 회피하고 있다 — 즉 안전성이 compose 파일이 아니라 파이프라인 호출부에 걸려 있다. 수동으로 docker compose --profile dev up -d 만 치면 4001 이 같이 뜬다.

06환경변수가 들어가는 경로

Jenkins Secret file (pv-common-env, pv-{profile}-env)
        │  cat 병합
        ▼
     .env  (워크스페이스, chmod 600, post 에서 삭제)
        ├── set -a; . ./.env    → 셸 변수 (Validate / Verify / Deploy)
        │       ├── --build-arg NEXT_PUBLIC_*  → Dockerfile ARG → 클라이언트 번들 인라인  ★빌드타임
        │       └── compose build.args 의 ${NEXT_PUBLIC_*:?...} 도 같은 값을 읽음
        └── env_file: .env      → 컨테이너 프로세스 환경변수                            ★런타임

빌드타임은 2개뿐(NEXT_PUBLIC_GOOGLE_MAPS_API_KEY, NEXT_PUBLIC_AWS_S3_BASE_URL)이며 이미지에 굳는다. 나머지는 전부 런타임이라 값 변경 후 컨테이너 재생성으로 반영된다. 키별 용도와 dev/prod 배치는 okf/system/configuration.md 표를 따른다.

07운영

배포

Jenkins → 잡 → Build with Parameters → PROFILE 선택 → Build. dev 는 dev 브랜치를 4010 으로, prod 는 main 브랜치를 4000/4001 로 올린다.

로컬에서 파이프라인과 동일하게 재현

# .env 를 준비한 뒤 (공통 + 프로파일 병합본)
docker build --target builder \
  --build-arg NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=... \
  --build-arg NEXT_PUBLIC_AWS_S3_BASE_URL=... -t pv-verify .   # = Verify 스테이지

docker compose --profile dev up --build       # 포그라운드
docker compose --profile dev up --build -d    # 백그라운드
docker compose down

롤백 — 수동, 파이프라인에 스테이지가 없다

이미지가 빌드번호로 태깅되고 최근 2개가 보존되므로 직전 버전으로 되돌릴 수는 있다. 다만 파이프라인에 롤백 경로가 구현돼 있지 않고, post 에서 .env 가 지워지므로 배포 호스트에서 .env 를 복구한 뒤 수동으로 수행해야 한다.

docker images | grep solar-pv-system          # 보존된 태그 확인 (최근 2개)
IMAGE_TAG=<이전_빌드번호> docker compose --profile prod up -d --wait app-prod-4000 app-prod-4001

--build 없이 up 하면 기존 이미지를 그대로 사용한다. 실제 환경에서 검증된 절차가 아니므로 도입 전 한 번 리허설할 것.
